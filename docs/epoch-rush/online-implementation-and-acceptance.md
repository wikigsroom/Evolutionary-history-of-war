# 联机实施路线、运维边界与验收计划

> 原始设计基线保留。v0.8.0 已有实现，实际模块、运行参数、交付范围与测试结果以 [实现报告](godot-v0.8-online-report.md) 为准；下文计划和验收目标不等同于已通过。

日期：2026-10-11。配套：[总体设计](online-system-design.md)、[协议草案](online-protocol.md)、[参数草案](online-defaults.example.json)。**以下是待执行的开发/验收计划，不是已通过的测试报告。**

## 1. 实施原则与第一步

第一步建立双真人、对称经济、两侧视角都正确的离线夹具，再建立两个客户端与一个 Headless 裁判闭环。先证明同一比赛能被两个身份正确操作，再做找人、开房和容错，避免把 UI 连通误当成对战一致性。

当前单机 v0.7.3 的存档、AI 经济、首都进化、动作素材、长屏 SafeUI 与触控保持独立回归。新的 PvP 配置不能偷偷改变单机玩法，也不能拿右侧 AI 倍率当真人补偿。联机运行中客户端不再拥有裁判权限。

BattleSession 最少暴露 `submit_action`、`read_state`、`consume_visual_events`、`local_side`、`connection_status`、`request_leave` 和 `result_received`。单机实现可以立即执行模型；联机实现返回 SUBMITTING，再在 command_result 中进入 APPLIED/REJECTED。

## 4. Headless 裁判的运行与计时

服务端入口不实例化 Main 菜单、BattleScreen、音频或纹理节点。加载纯战斗核心与必要规则 JSON，包括会影响 bodyRadius/muzzle 的动画元数据；专用导出时保留这些元数据，剥离可视资源并核查依赖。Godot 的 headless 标志只关闭显示，不会自动替当前 Main 入口写好对局服务。

由 RoomRuntime 驱动 step_tick，不用 UI 的 `_process(delta)` 作为裁判。GameModel.advance 当前对 delta 有上限，不能在服务器慢半秒时简单调用一次并把遗漏时间吞掉；服务端固定步进、有界追赶、记录落后时间，持续落后则停止分配新房并迁移或暂停。

控制层使用单调时钟计算心跳间隔，数据库时间锚点保存可跨进程恢复的截止期限；模拟冷却与生产用 tick。断线期限、准备期限和租约不能用停止推进的战斗 tick 表示。

已识别的接入/裁判/数据库服务故障进入 SERVER_RECOVERING。必须通过服务健康和全局控制记录区分平台故障与单玩家不响应；不能把所有掉线都免判，也不能只靠客户端报“服务器故障”。平台故障时间对相关离线预算的扣除/期限平移按故障 ID 幂等提交。

## 5. 提交与崩溃恢复的具体验收点

1. worker 接受命令后形成未提交模拟批次；公共画面不能提前广播。
2. 持久接口验证所有权、前一提交 tick 与载荷哈希，批次/结果/指令终态原子写入。
3. durable commit 返回后再发送权威状态与 APPLIED；批次重复提交取原响应。
4. 5 秒检查点只截取已提交边界；同时记录随机流、控制状态、序号与事件游标。
5. 进程死亡后，控制器增加 owner_epoch，从检查点与已提交日志重建。
6. 重放后状态哈希与提交历史一致才继续发布；不一致则冻结并按故障终止，不能随意选择一方客户端快照。

验收必须覆盖四个故障窗口：**收件后未提交、提交中、提交成功但确认没送达、结果成功但奖励通知没送达**。单次“断网以后能重新进入游戏”不覆盖任何这些幂等竞态。

严格恢复的前提是受控服务端构建可重放。验证失败时备选是持久化每个提交批次的精确权威状态差分，回放差分而不重新计算浮点战斗；要重新测写入放大、日志压缩和迁移容量。完全故障容忍不是只增加重试次数。

## 7. 发布门槛：掉线与故障注入

| 编号 | 场景 | 必须证明 |
| --- | --- | --- |
| R01 | 断网 3 / 10 / 30 / 90 秒 | 在期限内回原 match_id、原席位，保留真实当前战局 |
| R02 | 超过 120 秒单次恢复期 | 在线对手获得明确弃权结果；不能 late resume 复活本方 |
| R03 | 多次断线累计超 180 秒 | 累计计时不被重启或连线事件清零 |
| R04 | Wi-Fi ↔ 蜂窝、IP 变化 | 身份不依赖 IP；旧连接失效，新连接继续原序号 |
| R05 | 锁屏、切后台、系统杀进程后重新打开 | 自动发现原局；未主动投降，不新建替代房 |
| R06 | 两个 socket 同时恢复一个身份 | 一个有效 connection_epoch，旧连接不能控制军队 |
| R07 | 快照下载一半断链 | 有界内存与超时；重新全量同步，不应用残缺状态 |
| R08 | 技术暂停后回来、暂停额度耗尽 | 暂停时双方所有动作冻结；墙钟恢复期限仍减少 |
| R09 | 两人都掉线/交替掉线 | 双离线冻结且 60 秒终止；不会凭先后造出胜者或无限拖延 |
| R10 | 收到指令未提交时杀 worker | 不显示 APPLIED；重连明确未执行并封存该旧序号 |
| R11 | 提交成功、确认前杀 worker | 恢复原已执行结果；无二次扣费、二次招募或二次施法 |
| R12 | 裁判租约失效后旧进程恢复 | owner_epoch 阻止旧写入，只有新裁判继续 |
| R13 | 杀接入实例 / 重启 Redis | 原身份、匹配和对局路由从持久记录恢复，Redis 不决定赢家 |
| R14 | 数据库短暂断连/提交超时 | 停止承诺成功、明确恢复状态；不猜胜负或静默丢操作 |
| R15 | 检查点损坏/哈希错/日志缺失 | 取另一可验证版本；仍失败则 SERVER_ABORTED，无伪恢复 |
| R16 | 自然基地摧毁与超时弃权/投降竞态 | 只有一个结果，重复查询始终相同 |
| R17 | 结果提交但通知丢失/App 重启 | 同一结果可取，奖励至多一次 |
| R18 | 服务滚动更新与旧版本长局 | 旧局排空，客户端不因服务升级被判掉线弃权 |
| R19 | UI 重连成功但仍有过期瞄准/插值/音效 | 清旧状态；不重放历史技能、不播放爆炸风暴 |
| R20 | 客户端改 side、HP、金币、目标ID、快照 | 无法越权或覆盖裁判，错误和限流可观测 |
| R21 | 主库故障后同步备库接管、旧主恢复 | 已确认提交存在、旧主被隔离，无异步回滚或双主继续写 |

每个关键用例要在接受端/提交端不同边界重复执行；所有权、幂等和终局竞态至少运行 1000 次，不能只靠一张正常对战截图。

## 8. 移动设备与网络组合

至少两台真实 Android，包含用户的摩托罗拉 X30 或同机现场验证；原生 Windows 渲染与导出包核对不能替代 Android 网络/后台测试。

| 网络档 | 人工注入条件 | 预期 |
| --- | --- | --- |
| 同机回环 | 0–10ms RTT | 协议与动作结果正确，方便定位核心问题 |
| 正常同区 | RTT 40–100ms、轻微抖动 | 连续对战与即时提交反馈达标 |
| 一般移动 | RTT 150–250ms、±80ms 抖动、1% 丢包 | 画面插值可用，提交/拒绝清楚，无永久不同步 |
| 严重弱网 | RTT 300–500ms、5% 丢包、突发停顿 | 明确弱网或进入受控恢复，不能无限缓存或假装动作成功 |
| 极端断续 | 10% 丢包、数秒断连、重复恢复 | 指令不重复、内存有界；体验允许降级但身份与结果不混乱 |
| 真实网络切换 | Wi-Fi / 4G / 5G | 系统生命周期、DNS、TLS、地址变化和重新鉴权正常 |

本地用自建原生故障代理注入延迟、断流、重排序的应用消息/重复响应；完整 TCP 丢包需受控真实网络或允许的远端网络工具验证。应用层延迟模拟不能标作已测真实无线丢包。整个过程不调度 Docker、WSL 或本地模拟虚拟机。

## 9. 初步稳定性目标与指标

这些是上线门槛候选值，必须记录实测条件、样本量和失败原因。系统不可达、用户主动离开和网络身份错误分别统计，避免用筛掉所有失败样本的口径宣称稳定。

| 指标 | 首轮目标 |
| --- | --- |
| 兼容且服务可用时建房成功率 | ≥99.5%，失败错误可解释；不把满员等业务拒绝算技术崩溃 |
| 同区正常网络业务确认 | RTT≤100ms 时，从点击到 durable command_result P95≤300ms |
| UI 即时提交反馈 | 本机点击后约一帧内进入 SUBMITTING，不伪造成功 |
| 玩家普通重连 | 网络已恢复、凭证有效、服务器健康时 P95≤8 秒回到可操作状态；包含最多约 4.8 秒退避和状态下载 |
| 冷启动 App 恢复 | 单独统计资源启动耗时；候选 P95≤10 秒，不套用热重连数据 |
| 裁判崩溃恢复 | 可信检查点/日志完整时 P95≤15 秒；30 秒硬恢复上限 |
| 已提交回滚 / 重复指令 / 重复结算 / 双裁判 | 验收中 0 次，出现即阻断发布 |
| 正常负载模拟调度 | 30Hz，不持续丢 tick；满载固定步进循环 P99≤25ms，留出 33.3ms 节拍余量 |
| 持续运行 | 24 小时有代表性负载，无不断增长的队列/内存/孤儿房间；观察后稳态漂移目标≤10% |
| 对外服务可用性 | 稳定版长期目标 99.9%；演示与单机部署不宣称已达到 |

重连成功率按“期限内网络恢复且凭证有效的恢复请求”定义，人工断线矩阵至少 1000 次、成功≥99%；所有失败必须可定位。不能把网络始终没恢复的请求从玩家体验报告删掉；总体用户成功/失败还需单独公布。

观测至少采集：queue_wait、room_conflict、offer_expired、command_commit_latency、duplicates、sequence_gap、full_resync、ws_buffered_bytes、tick_lag、checkpoint_age、replay_hash_mismatch、lease_lost、resume_success/expired、platform_recovery、result_duplicate_conflict。日志含 build/protocol/ruleset/match、指令与代际字段，不含 token 或完整私有玩家状态。

## 10. 容量计算与增长方式

先测单局纯模拟 ms/tick、state_delta/full 大小、检查点压缩大小、100ms 提交日志大小、每房 RSS 和数据库 P95 写入延迟，再测多个房间一起运行。现有 Performance 脚本主要测渲染，不能拿其 FPS 估算服务端房数。

粗算单核房数上限可以从 `(33.3ms × 利用率预算) / 单局最坏耗时` 得到，再下调序列化、协议和突发开销；进程池的正式容量仍由混合房间满载压测确定。例如测得的单局耗时若翻倍，房数也应相应减半，而不是靠扩大缓冲让所有人的操作变迟。

建议首个公开灰度目标最多 50 房、100 名对战玩家，**这只是容量控制目标**，没有测试前不放开。通过后再增加到 100 / 250 房，配套增加多个原生工作进程/宿主；热房不做高风险实时迁移，优先分配新房、旧房排空，故障恢复路径独立承担异常转移。

当无健康容量时，匹配保留等待状态、建房给明确稍后重试，不进入“已找到对手但永远加载”的黑洞。比赛已开始后不降模拟规则、单位上限或伤害频率来隐藏机器过载。

Redis 缓存失效只降级查找速度；匹配票据和房间真值仍在 PostgreSQL。初期可以只用数据库与 Go 匹配循环，容量实测需要后再加 Redis；若启用其事务/脚本，要同样定义重建与过期行为。[Redis 事务文档](https://redis.io/docs/latest/develop/using-commands/transactions/)。

## 11. 灰度、版本与回滚

对局实现可按后续 0.8.x 系列发布，具体版本在开发完成后确定。联网开关由服务器 bootstrap 控制：关闭新匹配和新建房时仍允许已有比赛恢复与取结果；不能一关功能就把所有玩家踢成弃权。

每次构建保存 simulation_hash、协议、导出包、迁移版本和测试报告。数据库迁移先向后兼容扩字段，再切流，再清旧字段；运行中旧裁判固定自己的规则清单。回滚接入服务不能让旧客户端写新结构，也不能回滚已经发出的唯一结果。

上线前需明确部署区域、真实接入域名、预算/并发上限和恢复凭证存储方式。当前设计没有替用户购买主机、设置 DNS 或将后台发布到外部。

联机首次启用会新增身份、IP/连接日志、对局与战绩等实际数据处理；在发布前同步更新 SIDcloud 隐私说明和数据保留设置，按实际实现写，不沿用“单机无联网”的旧描述。此项是上线依赖，本次不擅自部署新隐私条款。

## 12. 最终交付应包含什么

可用客户端的两种入口、可恢复身份、原生服务端构建、服务部署与排空脚本、数据库迁移、通信协议、规则清单、运维指标、故障注入工具、真实移动端报告、可追溯安装包，以及复现六位同码并发、命令确认丢失和裁判重启的验收记录。

第一版“已完成”的定义是：两个真实玩家可以自由匹配或输入相同六位码进入同一局，执行同等规则，在可恢复的网络/进程故障后回到可信原局，且不会重复购买、不同步时代、私有信息泄露或重复结算。不能以房间界面和成功 socket 建连代替这一标准。
