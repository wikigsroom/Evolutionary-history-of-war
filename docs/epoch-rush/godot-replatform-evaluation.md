# Epoch Rush：Godot 重构可行性评估

> 2026-10-07：本文保留早期平台取舍和迁移起点。针对当前“系统性全面重构后，动作与演出是否更好”的判断，以 [最新专项评估](godot-system-rebuild-assessment.md) 为准；仓库现已存在独立 Godot 实现。

> 评估对象：当前 Phaser 3.90.0 + TypeScript + Vite + DOM HUD + Capacitor/Electron 方案  
> 候选方案：Godot 4.x + GDScript + Control UI + 2D Scene/Particles  
> 评估结论：浏览器优先时保留 Phaser 更稳；原生优先且同时重建动作与演出管线时，Godot 值得作为重构主线，先完成可对照验收的完整切片。

> 2026-10-06 补充：针对“系统性全面重构动作与演出”的评估见第 9 节。原生发行优先时，Godot 值得成为重构主线；最终表现优势必须由相同内容的对照验收确认。

## 1. 结论

如果“控制效果”指的是编辑器内拖拽 UI、统一主题、动画时间线、粒子和原生触控手感，Godot 的确会比当前的 DOM 模板 + CSS 覆盖方式更集中、更容易预览。Godot 的 `Control` 节点可以通过锚点和容器组织布局，`Theme` 资源可以从根节点级联到整棵 UI 树，官方主题编辑器也支持预览交互状态。这些能力适合制作方案 1 的像素卡片和弹窗体系。

如果“整体游戏效果”包含浏览器发布、现有 TypeScript 战斗规则、现有测试、Vite 开发流程和 HTML 可访问 UI，Godot 不会比当前方案更好，整体迁移反而会增加风险。当前项目是 2D 横向兵线战斗，正好属于 Phaser 的默认适用范围；项目已经有 Phaser 场景、摄像机、精灵动画、动态加载、粒子/弹道和 DOM HUD，现有能力不足的主要原因是 UI 结构和表现还需要系统重构，而不是引擎缺少基础能力。

因此建议：**保留 Phaser 作为正式产品运行时，先实施 v0.5 像素卡片指挥甲板；只在需要原生优先、编辑器驱动和多场景复杂动画时，另做 Godot 垂直切片验证。**

## 2. 当前项目已经具备的能力

- `src/core/` 将战斗、资源、时代、队列、主动道具、研究和存档规则放在 TypeScript 逻辑层，战斗状态可测试、可保存。
- `src/presentation/battle-scene.ts` 已经负责战场、摄像机、单位动作、攻击弹道、基地状态、炮塔和粒子效果；还有动态动画图集加载和效果对象上限。
- `src/ui/app.ts` 使用明确的 `data-action` 路由、键盘快捷键、触控瞄准、弹窗焦点管理、暂停和存档屏障。
- `src/ui/screens-v03.ts` 生成营地、战斗 HUD、进化、研究、炮塔、训练队列和结算界面；`src/ui/command-theme.css` 与 `src/ui/rounded-theme.css` 提供响应式 CSS。
- `src/main.ts` 使用 Phaser 3.90.0、Vite 和 Phaser Scale Manager；HTML UI 位于独立的 `#interface` 层，战场位于 `#game-world` Canvas。
- `capacitor.config.json` 和 Electron 打包路径已经存在，浏览器、Windows 和 Android 是当前交付路线。

这意味着目前的瓶颈是“UI 组件组织、像素资产一致性、状态反馈和 CSS 选择器冲突”，不是“无法绘制基地、单位或粒子”。

## 3. Godot 能带来的真实收益

### 3.1 UI 结构和主题

Godot 的 `Control`/`Container`/`Theme` 组合可以把顶部战况带、底部指挥甲板、进化弹窗和营地页面保存成可视化场景，减少现在由长模板字符串和多层 CSS 覆盖带来的维护成本。主题资源可以集中管理颜色、字体、StyleBox、图标和控件状态，并从父节点级联到子树。

这对方案 1 的价值很明确：可以制作一个 `PixelTheme.tres`，统一像素卡片、按钮、进度条、弹窗和焦点状态，再用 `BattleHud.tscn`、`CommandDeck.tscn`、`EvolutionModal.tscn` 组合界面。修改一处主题资源即可看到所有界面的更新。

### 3.2 动作、动画和粒子

Godot 可以把单位动画、命中闪白、受击位移、基地升级和场景特效组织在节点树、AnimationPlayer/Tween 和粒子节点中。`GPUParticles2D` 提供 2D 粒子发射、单次播放、材质和轨迹；低端设备可切换到 `CPUParticles2D`。这会让调参和预览更集中。

但 Phaser 3.90.0 也已经有独立的 `ParticleEmitter`、生命周期、颜色、发射区域、动画帧和事件能力；当前 `battle-scene.ts` 还有弹道、预览、效果池和 180 个瞬时效果上限。迁移到 Godot 不会自动增加打击感，仍然需要重做粒子素材、触发时机、镜头震动、命中停顿和音效层次。

### 3.3 输入和原生运行

Godot 可以把鼠标、触控、手柄和键盘动作统一映射到 InputMap，Control 节点也有明确的焦点与导航关系。若未来重点变成 Windows/Android/iOS 原生版本、手柄支持和多页面场景管理，Godot 的输入边界会更自然。

## 4. Godot 的代价和限制

### 4.1 浏览器交付会变复杂

Godot Web 导出运行在 `<canvas>` 中；这意味着当前依赖原生 HTML 的文本、键盘焦点、`aria-label`、文件输入、浏览器滚动和 DOM 调试都要改成 Godot 自己的 UI 或 JavaScript 桥接。官方 Web 导出文档还说明，多线程 Web 导出需要 SharedArrayBuffer 及跨源隔离响应头；单线程导出兼容性更好，但性能余量更小。Godot 4 的 C# 项目也不能导出 Web，因此如果继续保留浏览器版，实际应选择 GDScript。

当前项目使用 DOM HUD 的好处是：像素图集可以继续用 CSS 控制、文字和焦点容易检查、浏览器截图/自动化测试直接可用、静态资源可由 Vite 部署。迁移后这些能力需要重新实现。

### 4.2 现有 TypeScript 规则不能直接复用为原生 Godot 逻辑

`src/core/` 是当前项目最有价值的资产，但 Godot 原生运行时不会直接执行这套 TypeScript。完整迁移需要把 `Battle`、`types`、`combat`、`active-items`、`research`、`campaign-waves`、存档验证和测试全部翻译为 GDScript 或 C#，再重新建立资源加载、序列化和测试工具链。

可以通过浏览器 JavaScript 桥接暂时运行部分 TS，但这会把“Godot 场景 + JS 规则 + Web 专用桥接”绑在一起，原生 Android/Windows 交付和调试都会变复杂，不适合做正式架构。

### 4.3 资产和 QA 需要重建

当前运行清单、图片路径、动画图集、Sub2 生成记录、帧门禁、动作录像和 Vitest 都围绕 Phaser/Vite 组织。Godot 迁移后要重新建立 `.tscn`/`.tres` 资源、导入设置、SpriteFrames、AtlasTexture、动画门禁、截图 QA 和包校验。素材本身大多可以复用，但导入配置和锚点不能直接复用。

### 4.4 迁移会暂时冻结玩法迭代

重构期间如果同时迁移引擎、UI、动作、粒子和时代逻辑，很容易再次出现双方时代同步、训练队列、存档迁移或主动道具目标校验的回归问题。当前项目已经有这些规则的自动化测试，整体迁移会让原测试暂时失效，直到 GDScript 版本重新补齐。

## 5. 维度对比

| 维度 | 当前 Phaser + DOM | Godot 4.x |
| --- | --- | --- |
| 方案 1 像素 UI | CSS/DOM 可做，需拆分组件和清理覆盖层 | Control + Theme 更集中，编辑器预览更好 |
| 长文本、焦点、键盘、无障碍 | 原生 HTML 优势明显 | Canvas UI 需要重新设计可访问性 |
| 2D 精灵和兵线 | 已完成并有现成资产管线 | 能完成，但需要重建场景和动画资源 |
| 粒子和打击反馈 | 已有 Particle/Graphics/效果池能力 | 节点化粒子与动画调参更方便 |
| 摄像机和输入 | 已有拖动、滚轮、触控瞄准和快捷键 | InputMap 更集中，但要全部重接 |
| 浏览器部署 | Vite 静态部署，当前路线成熟 | Web 导出为 Canvas，需要处理导出限制和桥接 |
| Windows/Android/iOS | Electron/Capacitor 路线已存在 | 原生导出更统一，但要重建项目和存档 |
| 现有规则复用 | 直接复用 TypeScript 和测试 | 原生需翻译，Web 桥接不推荐 |
| 迁移风险 | 低，增量重构 | 高，属于完整重平台 |
| 近期收益 | 立即改善 UI 和交互 | 先付出较大迁移成本，收益较晚出现 |

## 6. 推荐路径

### 路径 A：继续 Phaser，完成 v0.5（推荐）

1. 按 [v0.5 像素卡片 UI 方案](ui-v0.5-pixel-card-update-plan.md) 拆出 `pixel-tokens.css`、组件 CSS 和分段 HUD 模板。
2. 通过 Sub2 `gpt-image-2.5` 生成像素图标图集 v2，统一锁定、冷却、时代、主动道具和弹窗图标。
3. 将 `battleHud()` 拆成顶部、辅助工具、底部甲板、指挥官托盘和弹窗组件；保留 `GameApp.paintHud()` 与 `data-action` 协议。
4. 把粒子和动作反馈整理成 Phaser 的事件驱动效果层，继续使用实际战斗事件，不把渲染对象写进存档。
5. 用现有 Vitest、浏览器截图和 Windows/Android 构建流程回归验证。

这条路径能直接解决当前用户反馈的 UI 协调、图标统一、控制状态、时代按钮反馈和战斗打击感问题，且不会暂停核心玩法开发。

### 路径 B：做一个 Godot 垂直切片（建议作为验证，不立即迁移）

单独建立不影响主项目的 Godot 试验目录，只实现一个固定场景：A3 对 A3、两座基地、五张招募卡、三个主动道具、进化弹窗、一个特种单位、一次命中粒子和一次基地受击反馈。试验使用与 Phaser 相同的 1280×720 和 844×390 截图基线，比较：

- UI 改动是否比 CSS 组件更快；
- 进化弹窗、队列、冷却和焦点状态是否更容易稳定；
- 单位动作、命中粒子和镜头震动是否更容易调出目标效果；
- Web 导出首屏、输入延迟、音频、存档和移动横屏是否满足当前交付目标。

垂直切片必须使用独立的最小状态模型，不能直接把生产 TypeScript 规则嵌入 Godot。只有当切片在 UI 迭代速度、打击反馈和目标平台上同时胜出，才考虑路线 C。

### 路径 C：完整 Godot 重平台（目前不推荐）

只有在以下条件同时成立时才值得执行：

- 产品目标转为 Windows/Android/iOS 原生优先，浏览器版降为附属版本或取消；
- 接受把 `src/core`、`src/presentation`、`src/ui` 和测试翻译到 GDScript/C#；
- 接受重新建立存档迁移、资产清单、动画门禁、截图 QA 和打包流水线；
- 先完成 Godot 垂直切片并通过性能、输入和存档验收。

完整重平台顺序应是：规则模型 → 存档格式和迁移 → 2D 战场与摄像机 → 单位动作 → 战斗事件和粒子 → HUD/营地 UI → 输入/触控 → 音频 → Web/Android/Windows 导出 → 全量 QA。不能从 UI 先迁移，也不能边迁移边修改时代规则。

## 7. 最终判断

对当前《一线万年：文明冲锋》的目标，Godot **会让 UI 场景编辑和原生动画调参更舒服，但不会让整体游戏控制效果自动优于现有方案**。当前最稳妥的选择是 Phaser + DOM 完成方案 1；它能复用现有 TypeScript 战斗规则、测试、浏览器交付、Sub2 素材和 Capacitor/Electron 包。

Godot 的正确定位是“经过垂直切片验证后的原生优先备选”，不是解决当前 UI 难看的直接补丁。若仅为像素 UI、更多粒子或更强打击感迁移，引擎成本大于收益；若未来明确转向原生发行、编辑器驱动的复杂场景和手柄优先，再启动 Godot 路线 C。

## 8. 动作效果与演出效果专项判断

### 8.1 当前 Phaser 动作层并不是临时方案

目前的 `src/presentation/motion.ts` 已经把单位动作拆成出生、移动、蓄力、释放、恢复、受击和死亡；`src/presentation/animation.ts` 根据逻辑时间戳选择攻击、行走、受击和死亡帧；`src/presentation/battle-scene.ts` 再消费真实战斗事件，处理枪口、弹道、命中环、碎屑、护盾、基地升级和镜头震动。

这套边界有三个优点：

1. 伤害和命中由 30Hz 规则层决定，动画不会反过来决定胜负。
2. 同一个战斗事件可以同时触发帧、粒子、音效、浮字和镜头反馈。
3. 降低动态效果时可以只减少装饰运动，不会丢失攻击预备、命中和状态变化。

所以当前“演出不够好”的主要原因是关键帧质量、武器挂点、动作幅度、命中停顿、粒子构图和声音混音仍需要继续制作；不是 Phaser 无法实现这些效果。

### 8.2 Godot 会在哪些地方更好

Godot 的 `AnimatedSprite2D` 适合管理帧动画和 SpriteFrames；`AnimationPlayer` 适合把帧、位置、缩放、武器后坐、受击闪白、粒子开关、音效和镜头轨道编排在同一条时间线上，并支持动画队列和过渡；Tween 则适合动态目标位置、镜头和数值插值。官方文档明确把 `AnimationPlayer` 定位为复杂、非平凡时序，把 Tween 定位为运行时目标值未知的插值工具。[AnimationPlayer](https://docs.godotengine.org/en/stable/classes/class_animationplayer.html) · [Tween](https://docs.godotengine.org/en/stable/classes/class_tween.html) · [2D sprite animation](https://docs.godotengine.org/en/latest/tutorials/2d/2d_sprite_animation.html)

因此，Godot 在以下演出上有明显的制作优势：

- 一次攻击可以在时间线上同时编辑蓄力、武器轨迹、命中帧、受击闪、粒子、音效和镜头停顿。
- 时代升级、基地崩塌、首领登场和战役过场可以做成可重复预览的演出资源。
- 特种单位的光环、旗帜、武器挂点和多部件动作可以保存为场景资源，设计师不必反复改 GDScript 数值。
- 同一演出可以通过速度、暂停、反向播放和分段跳转进行审查，适合做动作验收。

### 8.3 Godot 不会自动变好的部分

Godot 仍然需要正确的动作资产和演出设计。如果只是把当前的 `actorFrame()`、`fighterPose()` 和粒子调用逐行翻译为 GDScript，画面不会因为换引擎而自动变好。以下内容仍需重新制作：

- 每个兵种的待机、行走、蓄力、释放、恢复、受击和死亡关键帧。
- 长矛、弓、炮车、火枪、磁轨和冲锋的武器挂点与释放姿势。
- 受击方向、轻重单位位移、硬直、死亡退场和基地四阶段破损。
- 普通命中、破甲、护盾、治疗、烟幕、时代大招和基地摧毁的粒子构图。
- 40–60ms 命中停顿、80–120ms 重击镜头震动、声音层次和屏幕边缘反馈。
- 同屏几十个单位时的遮挡、层级、状态图标和特效预算。

`GPUParticles2D` 和 `CPUParticles2D` 都能提供 2D 粒子；前者硬件加速、后者更适合部分低端或 GPU 受限设备，官方文档也提醒两者在性能取舍上不同。[GPUParticles2D](https://docs.godotengine.org/en/stable/classes/class_gpuparticles2d.html) · [CPUParticles2D](https://docs.godotengine.org/en/stable/classes/class_cpuparticles2d.html) 这意味着 Godot 会改善粒子调参工具，但仍要由我们决定粒子数量、生命周期、颜色、遮挡和触发条件。

### 8.4 对本项目的预期差异

| 演出项目 | Godot 全面重构后的可能收益 | 是否保证更好 |
| --- | --- | --- |
| 普通单位走路/待机 | SpriteFrames 编辑更直观 | 否，关键帧仍决定质量 |
| 攻击时序 | AnimationPlayer 时间线更好调 | 只有保留逻辑事件门槛才会更好 |
| 受击与硬直 | 多轨动画、闪白、位移更容易编排 | 否，仍需设计受击权重 |
| 粒子和弹道 | 粒子节点、材质、轨迹调参更集中 | 否，粒子构图和预算仍是核心 |
| 基地升级/摧毁 | 场景和动画资源更适合做阶段演出 | 较可能更好 |
| 时代过场/首领登场 | 时间线和场景资源明显更强 | 较可能更好 |
| 同屏大量单位 | 需要重新测量节点、粒子和 Canvas 性能 | 不确定 |
| 浏览器端帧率与输入 | Canvas Web 导出增加额外验证 | 不能假设更好 |

### 8.5 如果真的迁移，正确的动作架构

不能把 Godot 的动画播放状态当作战斗真相。建议保持以下边界：

```text
BattleSimulation（固定 30Hz、可存档）
        ↓ BattleEvent / PoseCommand
PresentationDirector（事件时间线、命中停顿、镜头和音频）
        ↓
UnitScene / AnimatedSprite2D / AnimationPlayer / GPUParticles2D
```

- `BattleSimulation` 继续只产出 `windup`、`release`、`hit`、`status`、`death`、`evolve` 等事件。
- `PresentationDirector` 为每种武器和事件选择演出资源，负责合并同 tick 命中和限制效果预算。
- `AnimatedSprite2D` 播放连续帧，`AnimationPlayer` 管理攻击、受击、基地升级等多轨演出，Tween 负责运行时目标位置和镜头。
- 每个动作资源必须声明 `anticipation`、`release`、`recovery`、`hit-stop`、`muzzle`、`impact` 和 `audio` 标记，逻辑命中只认 `release` 标记对应的事件。
- `GPUParticles2D` 用于重复粒子，代码生成的轻量环形、浮字和警告仍由效果管理器统一回收。
- 同一套演出必须支持正常动态和降低动态两个版本；暂停时冻结演出时间线，恢复时不能重复消费旧事件。

### 8.6 专项结论

**Godot 的可视化动画与场景工具更便于制作和管理复杂演出；最终动作、画面与性能需要实测，不能据此认定其视觉上限天然高于 Phaser。**

如果团队愿意重新制作动作资产、建立 AnimationPlayer 演出库、编写事件导演和重做 QA，Godot 很可能在时代升级、基地摧毁、首领登场和多轨技能演出上胜出。对于普通单位的帧动画、像素命中和大量轻量粒子，Phaser 已经能达到同一效果，继续增量改造的风险更低。

所以迁移理由应该是“需要一套可视化的原生演出制作管线”，而不是“Godot 会自动修复动作和打击感”。

## 9. 系统性全面重构：动作、演出与 UI 的实际收益

### 9.1 本次结论

如果重构包括战斗规则、动作资源、事件时序、粒子、镜头、音效和方案 1 的 UI 组件，Godot 具备让当前作品明显进步的条件。预期收益最集中的部分是：攻击各阶段的协调、时代进化与基地变形、特种技能的多轨演出，以及整套 HUD 的可视化布局和统一主题。

这不意味着 Godot 的像素画面质量天然高于 Phaser。相同 sprite sheet、相同动作时序和相同效果参数，在两个引擎中可以得到相近结果。普通动作的质量首先取决于关键帧与动作设计；帧率、包体、加载和输入延迟必须实测。

在 Windows/Android 原生体验优先的前提下，推荐把 Godot 作为系统性重构的候选主线。如果浏览器即开即玩仍是主要交付目标，则应先比较 Web 首屏、触控、音频和性能，再决定是否全面迁移。不能仅为更换 UI 绘制方式承担整个规则系统的重写成本。

### 9.2 打磨前的两套代码快照

以下记录的是 2026-10-06 开始重做时的源码状态，用于说明重构起点，不是最终实现或性能结论。2026-10-07 的实际交付、完整对局、安装包和验证边界见 [Godot 成品交付记录](godot-polish-delivery.md)。

- 现有 Phaser 版的 `src/presentation/animation.ts` 用逻辑 tick 控制蓄力、释放、受击与步幅；`motion.ts` 按步兵、骑乘、战车、车辆、机甲调整姿态与武器运动。
- `src/presentation/battle-scene.ts` 已按真实战斗事件处理武器挂点、材质命中、碎屑、浮字和重击镜头反馈。因此不能把已有表现不佳归因于 Phaser 缺少这些能力。
- `src/core/occupancy.ts` 已包含体积间距、出口占用、移动约束和合法接敌；`tests/formation.test.ts` 与 `tests/era-independence.test.ts` 是迁移时必须保留的行为依据。
- 当前 `godot/scenes/` 只有入口 `Main.tscn`，菜单与 HUD 主要由脚本现场搭建，尚未形成可在编辑器中独立调整的兵卡、甲板、弹窗和单位场景库。
- 当前 Godot 单位只按状态播放一套统一的 6 帧动画；攻击动画循环与伤害冷却分别推进。`game_model.gd` 在攻击冷却归零时直接扣血，`battle_world.gd` 随后绘制飞向目标的弹道，未形成完整的蓄力—释放—飞行—命中同步。
- 当前 Godot 移动直接增加 x，目标只按 x 距离选择，缺少旧版体积占位、前排阻挡与合法接敌判定。训练队列不能代替战场上的攻击排队。
- 当前 Godot 招募卡固定读取 `U1%d.png`，没有随着我方时代切换卡图；训练订单记录了时代，但出场取当前时代。这些都是需要对照旧版规则检查的迁移差异。
- 当前 Godot 表现层尚未建立 `AnimationPlayer` 演出库、粒子节点资源、镜头导演和音频联动。它可作为技术骨架，不能据此宣称全面优于迁移前。

### 9.3 哪些效果最值得重建

| 对象 | 完整重构的具体做法 | 预期收益与条件 |
| --- | --- | --- |
| 行走、待机 | 分角色 SpriteFrames、脚底锚点、按移动距离推进步幅 | 解决滑步与抖动；仍依赖素材连续性 |
| 普通攻击 | 独立蓄力、释放、恢复阶段，武器挂点和命中 tick 同步 | 攻击意图更清楚，避免扣血与画面错位 |
| 受击与死亡 | 区分轻重、方向、材质；闪白、硬直、退场与音效联动 | 增加重量感；不能让每次受击都无条件打断攻击 |
| 特种单位与主动道具 | 可复用技能场景，分预警、释放、命中、残留四段 | 各技能形成辨识度，避免统一套用圆环 |
| 时代进化、基地摧毁 | AnimationPlayer 编排基地变化、镜头、粒子、音效和 UI 提示 | 是 Godot 时间线与场景资源最有价值的应用 |
| 方案 1 UI | Control/Container 场景、统一 Theme、像素九宫格边框、真实图标与状态层 | 更容易严格对照设计稿；默认控件外观仍需完全定制 |
| 同屏兵线与特效 | 效果池、事件合并、透明叠加预算、质量档位 | 收益取决于设备与场景压力，不能保证迁移后更快 |

Godot 的 `AnimationPlayer` 提供复杂时序动画及轨道编辑；`GPUParticles2D` 提供材质、单次发射和轨迹等配置；`Theme` 能集中管理字体、图标、颜色与 StyleBox，并向子控件传播。这些是制作工具优势，最终效果仍由资源和编排决定。参见官方 [AnimationPlayer](https://docs.godotengine.org/en/stable/classes/class_animationplayer.html)、[GPUParticles2D](https://docs.godotengine.org/en/stable/classes/class_gpuparticles2d.html)、[GUI skinning](https://docs.godotengine.org/en/stable/tutorials/ui/gui_skinning.html)。

### 9.4 建议的重构边界

```text
固定步长 BattleSimulation
  时代 / 经济 / 出营 / 占位 / 接敌 / 弹道 / 伤害 / 胜负
                         ↓ 带 tick 与实体 ID 的事件
PresentationDirector
  动作阶段 / 武器挂点 / 命中反馈 / 镜头 / 粒子 / 音效
                         ↓
UnitView + SkillScene + BaseView + BattleHUD
```

1. 战斗模型沿用当前 30Hz 固定步长与明确的数据边界。动画信号只触发表现，不能因丢帧、缩放、暂停或跳过演出而重复扣血。每个攻击的释放和命中都必须由模型记录。
2. 占位使用适合兵线玩法的确定性间距与阻挡规则。Godot 物理碰撞不会替我们决定短兵接敌、长兵越肩、远程输出与出营等待。
3. 普通像素兵种以逐帧动画为主，重型机械可增加分部件运动；AnimationPlayer 用于武器、闪白、粒子与音效的时间线。帧动画切换不需要为所有角色引入复杂骨骼混合。
4. Sub2 素材流程继续服务于关键帧与统一资产。生成后仍需检查轮廓一致性、脚底锚点、帧间尺寸、朝向、武器与透明边缘；增加帧数本身不能保证更流畅。
5. UI 按方案 1 拆成顶部战况、招募卡、道具卡、进化主按钮、指挥官托盘和弹窗。使用统一像素边框、字体、图标与禁用/冷却/选中状态，逐项对照设计稿，不能仅以换成 Control 节点作为完成标准。
6. 原有兵、付费训练订单、新招募兵和双方基地各自的时代规则必须保持一致，并通过回归测试确认；双方时代继续分别存储。

### 9.5 迁移投入与验收

素材 PNG、背景、音效、字体与配置可复用；TypeScript 战斗规则、浏览器 UI、存档接口和现有 Vitest 测试不能直接变成原生 GDScript 运行逻辑。需要逐模块迁移并建立对等用例，而非只翻译渲染代码。

建议先验收一个完整对局切片：近战、远程、重型各一种，独立时代升级、占位与训练出营，两个主动技能，基地受击与摧毁，方案 1 的完整 HUD。它是之后所有兵种与时代的制作模板。

验收至少包含：

- 同素材、同逻辑参数的动作对照：蓄力可读、武器与命中同步、脚底稳定、死亡不重复。
- 功能回归：双方时代独立、训练时代正确、单位不穿透、出营堵塞可恢复、暂停后不重复扣血。
- UI 对照：相同屏幕比例下，设计稿的战场占比、卡片层级、主按钮、字体和状态表达都落实；桌面和移动横屏分别检查。
- 性能：相同设备与压力场景测量帧耗时、输入延迟和特效峰值，分别记录合法兵线的代表场景与额外压力场景；尚无这些数据时不声称性能更好。此轮实际采用 24 单位代表场景和 60 单位人工密集压力场景，见交付记录。
- 完整对局：从菜单开始，经过招募、进化、战斗到胜败结算和再开一局。能导出 EXE/APK 只证明打包能力，不证明内容完成。

如果保留 Web 版，Godot 4 当前 Web 导出要求 WebAssembly/WebGL 2；单线程导出可避免多线程所需的跨源隔离配置，C# 项目当前不能导出 Web。因此该路线优先选 GDScript，并实测浏览器首屏、音频与移动输入。参见官方 [Web 导出说明](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)。
