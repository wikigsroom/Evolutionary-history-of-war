## 1. 路线与朝向

**旧版敌方朝向检查有错误。** 31 组敌方图集只是换色，仍面向右侧；原覆盖用例把“敌方不翻转”作为通过条件。现在模型为实体维护实际 `facing`，正常进攻、让位、撤退、驻防归队和攻击锁定分别更新方向，显示层随方向翻转精灵及脚底锚点。炮塔和敌方枪口效果也按左右阵营处理。

行走帧按真实移动距离推进，移动时不会因为刚刚攻击过而错误播放恢复动作。让位终点被占用时，单位留在后排等待合法空位，不会跳到远处的“最近空位”。撤退到家后可正常驻防，重新出征恢复前进朝向。

完整对局审计还发现远程让位的旧默认时长固定为 15 tick：例如 U22 在 0.5 秒内后移 108，实际达到自身速度约五倍。已按距离和兵种速度计算时长；缺少时长的旧存档也使用同一补全规则。固定单位保持阻挡，不被强迫侧移。

工程师部署炮台曾复制英雄实体的全部字段，包括让位、受击和硬直。复现中炮台出生于 700，下一帧跳到约 596.67。现在炮台使用新实体，仅接入自己的战斗属性；出生后保持部署点。证据见 [修复前](../../output/qa/godot-fixes/baseline-summon.log)、[修复后](../../output/qa/godot-fixes/repaired-summon.log)。

## 2. 生产队列

招募卡下方常驻五个订单槽，使用原订单兵种图标、顺序号和进度条；第一槽显示当前训练与剩余时间，完工遇出口堵塞显示等待警告。人口信息与队列一起展示。

点击订单槽可打开取消和退款操作。旧时代已付费订单保留原图标、原时代和原费用，进化后的招募卡显示新目录。队列依然按照 FIFO 训练与出营。

## 3. 地图与镜头

取消整张地图缩进单屏的布局，保持模型战线 1600，视觉边界扩展至 -80～1680，留出两座巨大基地的完整外轮廓。我方基地位于最左、敌方位于最右。

1280×720 时，镜头约显示 1056 的世界宽度；允许左右移动约 704。鼠标拖拽、滚轮、触屏拖拽、A/D 与方向键可移动镜头；Home/End 和右上图标可定位两侧基地，也可跟随英雄或前线。小地图显示兵线、基地与当前视野，支持点击/拖拽定位。

拖拽超过阈值只移动地图；施放使用抬起时的轻点。暂停、取消触摸、第二根手指与失去焦点时清理手势状态。保存对局时保留镜头位置和跟随模式，继续游戏后恢复。选点根据当前镜头转换为世界坐标。

## 4. 主动道具

基线复现显示三种道具已有模型效果，鼠标和触屏能消耗次数并改变状态；“完全无功能”的描述没有在该基线中复现。但选点、取消、反馈和触屏路由确有问题，本轮逐项修正。

| 道具 | 输入与实际效果 | 反馈 |
| --- | --- | --- |
| 战鼓 / Z | 即时施放，增加范围友军攻击并推进训练，维持 8 秒 | 友军状态图标、绿色持续条、冷却与次数 |
| 烟幕 / X | 先选择，再轻点战场；范围减速 35%，维持 5 秒 | 区域预览、部署提示、烟幕与持续条 |
| 时序补给 / C | 即时增加 65 金币、15 军令并推进训练 | 资源跳变、提示、训练进度与冷却 |

再次点击已选中的烟幕可取消；即时道具会清除旧目标选择。右键、Esc/返回和取消按钮正确关闭选点。拖动地图不消耗次数；非法坐标、冷却和暂停拒绝施放。烟幕到期不残留额外减速尾巴，道具冷却、次数与持续状态可从磁盘恢复。

Godot 原始触屏事件通过明确的输入路由处理，去重由触控模拟的鼠标事件，HUD 按钮与地图有清楚的命中边界。

## 5. 其他修正

- 战场效果裁剪在顶部信息与底部甲板之间；UI、托盘和弹窗使用明确层级，烟幕不会盖住道具按钮。
- 收集奖励的目的地保持在固定 HUD 坐标，地图移动不会把提示移走。
- 删除/出售的炮塔视图同步移除，敌方炮塔朝向正确。
- 旧存档补全缺失朝向、动作时点、队列时长与道具字段；错误类型的恢复数据受到校验。
- 平局单独计入 `draws`，不计入失败，也不发首通奖励；重复提交不增加次数，旧档安全补默认值。

### 性能与限制

本机 RTX 3060、原生 OpenGL Compatibility、1280×720、关闭垂直同步，测量完整帧间隔；分别初始化 24/60 单位并持续触发粒子，当前镜头只显示其中一部分。60 单位是人工密集压力布局，不是合法单战线站位。

最新测量见 [performance.json](../../output/qa/godot-fixes/performance.json)。代表场景 600 帧的中位数/95 分位为 2.567/4.108ms，压力场景 540 帧为 4.091/12.049ms；最大分别为 7.071ms 和 32.737ms。采样结束时镜头内存活角色分别为 16 和 45。压力场景包含切换后建立视图的首帧间隔，最大值发生在该间隔。Godot 内置过程耗时为监视器快照，不作为逐帧 CPU 计时或帧预算依据。

首轮保留在 [performance-first-pass.json](../../output/qa/godot-fixes/performance-first-pass.json)：24 单位 95 分位 18.825ms、最大 1141.598ms；60 单位 95 分位 16.820ms、最大 61.983ms。因出现异常长帧，追加相同场景测量；两轮数据完整保留，尚未隔离首轮长帧的原因。这些样本不能证明所有场景稳定 60fps 或优于 Phaser，也不能作为手机性能保证。

当前没有 Android 真机的安装、系统手势、发热和续航测量。Windows 已完成独立启动和成品资源包的引擎事件复验；外部 OS 鼠标自动化此前无法初始化，所以尚不能把这些结果称为物理鼠标/触摸延迟实测。未启动 Docker、WSL、模拟器或浏览器测试标签页。

本轮修复的是上述可复现问题与检查范围内的规则/交互故障；作品的视觉质量、完整难度平衡和未知设备行为仍需试玩。当前 Godot 技术收益与继续制作目标见 [全面重构评估](godot-system-rebuild-assessment.md)。
