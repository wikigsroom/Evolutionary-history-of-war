# Age of War 前两部复核与重做方案

日期：2026-10-05。检查对象：《一线万年：文明冲锋》v0.2.0。范围按用户确认，仅包括 Age of War 1、2。

**结论：当前版本存在核心规则偏差、默认体验阻断和动作资产不足，应该重做战斗规则与表现契约。上一轮把“功能有代码、技术检查通过”扩大成了“玩法与动作已合格”，这个验收判断不成立。**

本文件是问题检查与后续解决方案。实测、源码结论、参考作品事实、拟议设计分别注明；方案尚未接入游戏，现有安装包仍为 v0.2.0。

## 1. 前两部应当学到什么

### 1.1 已核实的参考事实

| 项目 | Age of War 1 | Age of War 2 | 对当前项目的意义 |
| --- | --- | --- | --- |
| 核心目标 | 保住己方基地，摧毁对手基地 | 延续攻防与文明进化 | 对局重心是生产、阵线与换代时机 |
| 内容规模 | 作者说明：5 个时代、16 种单位、15 种炮塔 | 官方手机版说明：7 个时代、29 类单位 | 内容数量不能代替完整进化过程；手机版数量不当作 Flash 每项参数的证明 |
| 时代经验 | 游戏内说明：击杀敌军、己方单位阵亡均获得 XP | 官方攻略也明确己方阵亡提供 XP | 升级速度应当和战斗交换联系起来 |
| 特殊攻击 | 游戏内说明：各时代有自己的特殊攻击，使用后等待冷却 | 官方攻略：特殊攻击与进化都消耗 XP | 两代资源设计不同，不能混写为同一条规则 |
| 同时代强化 | 本轮没有确认与二代相同的金币强化系统 | 官方攻略明确：金币强化兵种；部分单位先被锁定 | 二代的“买强化还是继续出兵”是独立决策 |
| 克制 | 不借用二代图表声称一代也完全相同 | 官方克制图：步兵 → 支援 → 反装甲 → 重型 → 步兵 | 当前的伤害类型/轻重装系数，不能替代这套兵种关系 |
| 操作组织 | 小型图标入口，分层切换单位、防御等命令 | 官方 HUD 图按单位、炮塔、特殊、强化分组，详情按需出现 | 常驻信息应服务战场，不把营地说明挤进战斗 |

来源：[作者的一代发布页](https://www.newgrounds.com/portal/view/408209)、[一代作者说明](https://www.kongregate.com/en/games/louissi/age-of-war)、[二代官方攻略](https://www.maxgames.com/guides/age-of-war-2.html)、[二代官方克制图](https://www.maxgames.com/images/guides/age-of-war-2-3.jpg)、[二代官方手机版介绍](https://play.google.com/store/apps/details?hl=en&id=com.maxgames.aow2)。

第一部实际进入作者上传的播放器，核对了游戏内说明、初始 HUD 与出兵入口。第二部核对官方攻略、界面图和克制图。本轮没有完成两部完整通关，也没有从原作程序核定碰撞盒、所有攻击距离、每项 XP 数值与精确近战接敌数量。下面的占位算法、数值目标和素材规格是**本项目拟议实现**，不冒充原作内部源码。

### 1.2 核心爽感的因果关系

先出前排稳住接战位置，后出远程叠加火力；交战产生金币与经验，再在补兵、强化、防御、特殊攻击和进化之间取舍。抢先换代后，把新兵真正送到前线，利用技术差距打穿旧阵线。

这里的爽感来自“看得懂为什么打赢”：前排替后排争取输出时间；死去的前排让后续部队补位；新技术改变攻击方式与阵形；一发炮弹或一次时代大招制造推进窗口。只是把血量、攻击倍率变大，再增加更多技能和收集页面，无法建立这条循环。

## 2. 问题一：UI、图标与字体

### 2.1 检查结果

| 缺陷 | 实际证据 | 造成的体验 |
| --- | --- | --- |
| 圆角不足、面板过重 | 当前兵卡、技能卡、进化按钮计算样式均为 5px 圆角 | 方形框与描边主导画面，像管理面板 |
| 图标存在，但文字仍占主导 | 每张卡常驻名称、货币词、费用、快捷键；顶部资源重复标签；底部额外英雄状态和军令 | 小图标没成为主要识别方式 |
| 常驻结构过多 | 顶部两方基地、三种资源；第二层视野操作；底部兵卡、英雄、军令、技能、进化、防务 | 战斗视线不断被面板分散 |
| 手机字号太小 | 844×390 实测：兵种和技能名称 10px，价格行 9px | 小字密集，画面清楚也难以快速读数 |
| 字体未真正选型 | CSS 使用 Microsoft YaHei/PingFang；部分数字混用 Consolas；战场浮字另写微软雅黑 | 字重、数字宽度和卡通美术语言不统一 |
| 手机全宽战场带不足 | 上方控件延伸至 y=109；底栏从 y=272 开始，高 118；中间连续全宽空间仅 163px | 在 390px 高度中仅约 42% 留给完整战场带 |

最后一项是垂直布局测量，不是“58% 的画面像素被遮挡”：小地图只占部分宽度。问题是主战斗带被上下常驻结构夹住。

### 2.2 重做方案

视觉方向定为**圆润、清楚的卡通战争界面**：象牙色或深墨绿的薄浮层，暖金主动作，蓝红阵营提示。避免大面积玻璃面板叠框；面板 20–24px、兵卡 16–20px、资源胶囊 999px 圆角，主要命令用圆形按钮。图标和兵种剪影具有明确轮廓，细节数量低于战场角色。

布局按操作频率组织：

1. **顶部**：两方基地血条、金币和 XP、暂停；时钟退为辅助。英雄扩展启用时，能量放在英雄按钮的环形表盘中。
2. **底部左侧**：当前时代 4 张大头像兵卡，只常驻费用数字；角色名、射程、克制进入按需说明。
3. **队列**：训练缩略图与进度环；满员、出口堵塞分别显示人口和门口图标，不能都叫“待出营”。
4. **底部右侧**：醒目的时代图标与 XP 环、时代大招、炮塔入口；英雄军令折入英雄按钮。
5. **小地图**：默认收起为小型视野入口；拖动、点击定位仍可用。新手提示出现一次后退出常驻层。
6. **营地**：一个明确的“开战”主入口；完整文明对战默认可达。收藏、图鉴、构筑通过图标入口展开，取消多层重复口号和英文副标。

图标分工：兵种、时代、炮塔、大招使用本项目生成的彩色图标；暂停、设置、返回使用统一的圆端 SVG 图标家族，可采用 [Lucide](https://lucide.dev/)。费用与血量保留数字，首次使用保留必要短标签；纯图标按钮配置可读名称，触屏点击可打开说明，不能仅依靠鼠标悬停。

字体选择：

| 用途 | 选型 | 原因与接入方式 |
| --- | --- | --- |
| HUD、卡片、说明 | [资源圆体 Resource Han Rounded](https://github.com/CyanoHao/Resource-Han-Rounded) | 圆润中文字形适合卡通界面；采用官方预编译字体，检查简体字覆盖、字重与跨端显示，再在 Windows 本地制作网页子集 |
| 游戏标题、进化大字 | [得意黑 Smiley Sans](https://github.com/atelier-anchor/smiley-sans) | 有手绘美术字特征，用在少量大字；作者明确不推荐手机界面正文，因此不用作 HUD 小字 |
| 高频数字 | 优先正文同家族，经实测选择等宽数字配置 | XP、金币和冷却更新时保持宽度稳定；不能凭 CSS 属性假定字体已有对应特性 |

两种字体均按其 OFL 许可证随包保留许可文件；本地加载，避免外部字体 CDN。资源圆体仓库的源码构建说明涉及 Linux/WSL，本项目使用预编译发行文件，遵守禁止 WSL 的约束。此轮完成选型，尚未下载或接入运行字体。

### 2.3 验收

- 1280×720 与 844×390 两档先通过：常驻 HUD 的顶部和底部高度合计目标分别不超过视口 25%、35%；移动端小地图默认折叠。目标是本项目标准，不是原作规格。
- 手机主要数字 14px 起，必要短标签 12px 起；说明正文 16px 起。删掉信息优先于继续缩小字号。
- 游戏主操作采用至少 48×48 CSS px 的触控区域；图标本体可以更小。PC 保留快捷键与焦点状态。
- 不读长说明，也能找出兵、进化、炮塔、大招；禁用原因通过图标和短提示表达。
- 本地字体加载失败有可读回退；中文兵名无缺字；数字更新不卡位。

## 3. 问题二：动作、攻击与受击表现

### 3.1 检查结果

目前所谓 26 套动作主要是 26 套切片配置，运动由一个通用函数驱动，不能据此声称 26 个角色都有合格的独立动作设计。

| 缺陷 | 源码事实 | 必须改到哪里 |
| --- | --- | --- |
| 步行像摆纸片 | 腿用正弦转角，身体上下浮动；缺少脚掌支撑与重心转移 | 素材姿态、步态与位移共同重做 |
| 挥砍、刺击、投掷缺乏区分 | 大多数近战共用武器旋转；弓与枪只做小幅角度/位置差异 | 按兵器编排攻击，不按一个 ranged 布尔值代替 |
| 肢体缺少真实关联 | 身体、手、武器都是同一容器中的兄弟图像，没有肩—肘—腕层级 | 全帧素材或真正层级骨骼；平铺切片不能继续冒充完整骨骼 |
| 命中效果位置不准 | 受击高度按单位类别写固定值；枪口统一偏移 26px | 在动作帧定义手、武器端、枪口与受击挂点 |
| 特效语义错误 | 按时代选择石头/金属命中特效；W01 投石也进入近战划线分支；W06 骑兵与 W07 电弧进入枪口分支 | 武器事件和受击材质分别路由 |
| 受击、死亡套路单一 | 通用偏移、转角与整图倒下淡出 | 区分软目标、甲胄、坐骑、车辆、机甲，保留清晰轮廓 |
| 降低动态关掉必要动作 | `fighterPose` 提前返回空部件姿态 | 保留攻击/命中提示，只减弱震屏与装饰运动 |

代码位置：`src/presentation/motion.ts:14`、`:30`、`:36`，`src/presentation/battle-scene.ts:109`、`:148`、`:158`。

### 3.2 全单位的动作方案

以**完整姿态帧动画为主**。复杂英雄或装置可以用经过验证的层级骨骼辅助，但不再以通用摆动函数作为全部动作的主方案。每个单位都必须有自己的素材、挂点与时序表。

先按 8 类动作语法组织，再映射全部 20 个兵种与 6 名英雄：

| 动作族 | 要看见的动作 | 代表对象 |
| --- | --- | --- |
| 盾与挥砍 | 蓄力、踏步、挥砍、收势；盾手和持械手协同 | U11、U21、U31、U51；H03 |
| 长矛刺击 | 枪尖先后移，再水平刺出，身体与握持手同步 | U13、U23、U33、U53 |
| 投掷与鼓舞 | 摆臂抛物、释放、复位；击鼓用双手落槌 | U12、U14 |
| 弓弩 | 拉弓或弩击发、明确释放点、装填 | U22、U32；H02、H06 |
| 火器 | 举枪、击发、枪口后坐、再瞄准 | U41、U42、U43、U52；H04 |
| 骑乘与战车 | 四足步态、骑手稳定、武器接战；车轮与地面速度一致 | U24、U34 |
| 火炮车辆 | 履带前进、炮管后坐、车体缓冲、炮口烟 | U44；H04 部署的装置 |
| 机甲与能量 | 重量感落足、能量蓄积、发射和冷却 | U54；H05 |

英雄额外逐个设计招牌动作：H01 砺川的旗枪冲锋、H02 岚翎的弓箭攻击、H03 铎山的盾牌动作、H04 绮衡的军械部署、H05 溯青的时序施法、H06 麦穗的军令支援。动作族允许共享节奏规范，不能让不同角色共用一组不匹配的姿态。兵器对应现有角色数据，新增姿态在制作时逐个落实。

起始制作规格：待机 4 帧、行走 8 帧、普通攻击 6 帧、受击 3 帧、死亡 6 帧；英雄另有招牌技能序列。帧数是制作预算，最终以实际动作是否顺畅调整，不能用凑够帧数验收。

素材生产沿用用户指定的 **Sub2API**。使用 [sprite-pipeline](C:/Users/carzy/.codex/plugins/cache/openai-api-curated/game-studio/5fd93af4/skills/sprite-pipeline/SKILL.md) 的一致性流程：先定角色标准帧，再以参考图生成整条动作序列，统一缩放和脚底锚点，制作帧预览，最后放进引擎检查。每条序列检查服装、脸、武器、比例和朝向；透明背景或抠像结果有瑕疵必须修复或重做。不能逐帧独立生成后忽略角色漂移。

### 3.3 动作与规则共用一个时序

`移动/排队 → 攻击前摇 → 释放事件 → 命中或弹道 → 后摇 → 下一次攻击`。

- 近战伤害落在武器接触帧；枪弹从枪口挂点出发；受击反馈来自真实结算事件。
- `attackClip`、`releaseTick`、`recoveryTicks`、`bodyFootprint`、`muzzleSocket`、`hitSocket` 写入共享数据契约。渲染可以插值，不能自行循环制造假命中。
- 目标前摇期间死亡、击退出射程或被打断，要有取消/挥空规则；不能扣血发生了，画面仍没挥到。
- 命中特效按皮肉、布、木、石、甲、机械、护盾分类；普通轻击保持克制，重炮和终结技有清楚的强弱差异。
- 已有命中闪色可保留并校准；增加有节奏的冲击帧与声音，不把每一击都做成全屏震动。
- 打击停顿仅影响受击对象/表现采样，明确如何与固定模拟步长协调，不能随意暂停整场模拟。

### 3.4 验收与可行性

先制作盾兵、投掷兵、火枪兵、炮车四个代表，以慢放与原速录像验证脚不滑、武器不脱手、命中对应释放帧，再扩展到全部角色。两阵营优先复用动画，通过朝向与队伍标识区分，避免无意义复制帧。

单角色当前标准预算约 27 帧；26 角色约 702 帧，按 160×160 RGBA 粗估约 69MiB，未计英雄技能、较大车辆帧、图集空白、背景和设备开销。这是预算估算，不是 GPU 测量。按需加载，并保留仍在场的旧时代单位所需图集；不能进化后立即卸载其动作。全部新图集要重新做峰值内存验证。

## 4. 问题三：时代、跨代与兵种进化

### 4.1 不是“有 evolve 函数”就完成核心玩法

现有代码能消耗学识切换时代，切换训练目录、提升基地/英雄参数，播放背景变化。这部分存在，但默认首关被锁为 A1，系统规则与表现又削弱了进化的意义。

| 缺陷 | 证据 | 修正方向 |
| --- | --- | --- |
| 首局根本不能进化 | M01 起始 A1、最高 A1；实际按钮“已达本局上限” | 默认完整文明对战；教学第一局至少演示一次跨代 |
| 没交战也积累进化经验 | 学识被动 1.5/秒；仅两基地的受控场景约 106.67 秒就可到 A2 | 战斗经验为主要来源，取消核心模式的被动 XP |
| 阵亡经验缺失 | `kill` 只给对方学识；己方 U11 阵亡自己得到 0，对方得到 8 | 明确击杀 XP 和己方损失 XP，死亡事件只结算一次 |
| 同时代金币强化缺失 | 当前升级只在进化后免费三选一 | 增加兵种攻击、防护、射程与重型解锁等有限强化 |
| 二代的大招取舍缺失 | 技能消费独立能量，不影响学识 | 核心模式的时代大招与进化共享 XP；英雄技能另属本项目扩展 |
| 克制环不完整 | 伤害按 physical/pierce/blast/energy × light/heavy/base；无步兵到支援等类别关系 | 明确兵种类别克制，并和装甲公式避免重复放大 |
| 第一时代没有重型兵 | U14 是鼓手、非 heavy；U13 的反装甲职责第一时代缺少对应目标 | 调整第四槽职能，使首次对局就有可理解的对抗关系 |
| 英雄跨代缺少视觉更新 | 英雄 eraId 变化，contentId 与美术仍相同 | 若英雄随科技成长，给明确时代装备/武器阶段 |
| 换代控制整个环境 | 背景只跟随玩家时代，全战场一起换 | 中性共同地形、双方基地与局部设施各自表现时代 |
| 进化总被弹窗中断 | 玩家进化立即暂停，等待三选一 | 核心模式直接进化，短过渡不中断战线压力 |

### 4.2 明确三种成长

| 成长 | 改什么 | 玩家看见什么 |
| --- | --- | --- |
| 同时代军事强化 | 金币购买有限档位：步兵防护、支援攻击/射程、重型解锁等 | 对应类别升级标记与效果；继续出兵和买强化存在成本取舍 |
| 文明跨代 | XP 门槛、当前时代训练目录、防御目录、基地外观与时代大招 | 新图标、新武器、新攻击方式、新基地，而非仅改数值标签 |
| 兵种换代 | 新时代生产新兵；旧部队继续承担前线任务 | 新旧兵同场，逐渐替换；技术优势要经过生产和抵达前线兑现 |

**建议采用“生产目录换代、旧兵继续作战”的清楚规则。**当前旧兵与旧训练订单保留出生时代，不能仅凭它们没有瞬间变身就判为程序错误；这项具体保留政策在本方案中作为本项目规则，不声称本轮已经逐项核实原作。若加入场上晋升，必须明确价格、目标与生命继承；避免囤最便宜旧兵，免费转成昂贵新兵。

推荐训练订单在进化时保留已付价与出生时代，并清楚显示旧时代角标；后续点击生产采用新目录。旧炮塔允许继续使用，再通过出售/改建换新，不默认免费变成高级炮。强化的继承按兵种类别明确配置，不能拿“进化三选一”同时代替所有成长。

金币以初始预算和击杀赏金支撑出兵、强化与炮塔。当前 8/秒的基础收入也需重新衡量；若保留少量保底收入，作为本项目的防破产设计单独标明并限制，不让等待替代交战。己方阵亡提供的是 XP，不是额外金币；免费召唤、自然到期与取消训练不得用于刷阵亡经验。核心模式优先采用二代的 XP 争用关系，英雄独立能量作为扩展规则清楚区分。

### 4.3 保持五时代的可行范围，重做时代身份

此项目已有五时代内容，先把这五个时代做成完整、有手感的对局。学习二代的强化与克制，不为了对齐官方数量立即扩成七时代。

| 时代 | 战斗身份 | 玩家能够识别的变化 |
| --- | --- | --- |
| 石器 | 慢节奏肉搏、投掷与兽骑压阵 | 盾兵挡线、投掷后排、长矛对大型目标；重新处理鼓手第四槽职能 |
| 青铜 | 阵列、长矛与战车首次接战 | 武器长度、甲胄、战车蓄势冲击，而非套旧兵倍率 |
| 王国 | 重甲、弩线、骑士突破 | 更坚韧前排与更稳定远程；骑兵的首击优势可读 |
| 工业 | 弹道、炮击与范围压制 | 枪口与装填、炮车射程、炮弹到达后爆炸；阵线站位影响溅射 |
| 轨道 | 高效远程、能量与机甲压阵 | 明确能量武器、护盾命中与机甲重量；克制仍然有用 |

已有战车首击、骑士首击、炮车溅射、电弧链等能力可作为设计材料。它们的存在不代表已经有足够战术差异；要在正确占位系统上重新衡量收益。

跨代应有可见优势，也有出兵时间、经济与兵种搭配的约束。先同代比较各类别，再测领先一代与落后一代的组合，记录击杀时间、金币交换、阵线推进距离，避免写一个“高代一定赢”硬规则。

### 4.4 验收

- 默认新档无需先通关或进入开发场景，就能体验第一次进化。
- 一场标准完整对局可从 A1 推进到 A5；不要求每局都拖到 A5 才能获胜。
- 两方时代独立，新旧部队可同场；进化更新的兵卡、基地、武器与大招能被肉眼识别。
- 同时代强化确实消耗金币并改变结果；时代大招消费 XP 后，下一次进化时间会相应推迟。
- 空战场不被动涨 XP；己方阵亡和击杀奖励有独立、去重的结算记录。
- 用同金币预算测跨代组合；除装甲差异外，有明确兵种类别克制。所有目标参数由试玩校准，不照搬未核实的原作数值。

## 5. 问题四：人物占位与攻击排队

### 5.1 当前问题已经复现

1. `move` 只检查 `ally.id % 3 === entity.id % 3` 的同类单位，并额外受射程条件限制；单位编号变成三条隐藏逻辑通道。
2. 画面也按编号余数做 ±7px 行偏移和层级，但这些不是玩家可选择的真实战线。
3. 英雄、召唤物未进入同一套友方阻挡；所有新兵直接生成在 x=150/1450，生产完成只检查人口上限。
4. “最多三个近战接敌”统计的是同目标的前摇/冷却人数，不是身体接触、队首权限和武器可达性。
5. 普通士兵逻辑半径仅 12，渲染身高约 110，缺少把身体宽度、脚底锚点与规则尺寸连接起来的元数据。
6. 击退直接改坐标；没有统一队形重排和重叠修正步骤。

受控复现：前排位于 x=600，后排从 x=540 前进，最终位于 x=594.26，两者逻辑身体重叠 18.26px；出口被固定敌军堵住时，3 个正常付费训练订单仍全部在 x=150 出生；3 名重叠近战可同时开始攻击同一个敌人。它们说明当前实现缺少稳定的占位契约，不是正常原作完整对局的录像。

代码位置：`src/core/combat.ts:32`、`:125`、`:221`，`src/core/battle.ts:72`、`:211`，`src/presentation/battle-scene.ts:114`、`:196`。

### 5.2 四种“队列”分开定义

| 队列/阶段 | 解决的问题 | 拟议规则 |
| --- | --- | --- |
| 训练队列 | 钱已花，训练顺序是什么 | 先进先出、单项进度、明确取消退款 |
| 出营等待 | 训练完成，门口是否有空间 | 无合法位置则保留完成订单，显示“出口堵塞”图标 |
| 行军队形 | 部队如何向前、何时停止 | 单逻辑地面战线；统一身体尺寸与前后顺序；不能按编号决定穿人 |
| 接敌与攻击 | 谁能攻击、谁继续等待 | 前方可达近战接敌；后排远程按各自射程并行输出，阵亡后补位 |

**排队不等于全军轮流攻击。**远程在有效射程内可以同时开火；近战是否能越过一名友军刺击由武器规则决定。原作的精确重叠许可与接触数量本轮未全部核定，因此不会把“所有兵只能一对一”写成两部的已证实事实。

拟议阵线示意（不是原作内部碰撞图）：

```mermaid
flowchart LR
    B[己方基地 / 训练] --> Q[出营空间检查]
    Q --> R[远程后排]
    R --> W[等待的近战]
    W --> F[己方队首接敌]
    F --- E[敌方队首接敌]
    R -. 各自射程内并行射击 .-> E
    F -. 阵亡后释放占位 .-> W
```

### 5.3 可实现的占位规则

- 每个地面实体具有 `bodyWidth`、前后间隙、攻击可达范围、允许越肩刺击/穿透等明确属性；身体尺寸不包含飘动披风、武器长端与阴影。
- 按真实 x 位置与稳定的入队顺序维护队形。顺序产生于生产和运动，不能由 `id % 3` 决定；出兵先后应有战术意义。
- 普通移动先计算期望位置，再由统一阻挡步骤约束；不能每个单位独立写 x 后忘记修正相互穿透。
- 短兵器从队首接战；长矛只有配置允许且距离可达时才能越肩输出。敌人在友军身体后面且武器规则不允许越肩，则等待。
- 远程在前方射程内停驻并射击。允许的视觉错位或压缩站位要有上限，不能用随机行偏移掩盖无限重叠，也不把远程锁成“每次只能一个人攻击”。
- 英雄和召唤物也有身体和位置规则。撤回让行、冲锋通过与落点修正分别定义；特殊技能不拥有永久穿人权限。
- 死亡立即释放逻辑身体；尸体仅留在表现层。下一位推进时保持队形，不瞬移进死者中心、不重复抢占接战位。
- 击退、突进和召唤结束后统一修正非法重叠；炮弹允许飞越友军，敌军命中与溅射按武器规则结算。
- 基地附近满线时保留出营项目，空间和人口是两个不同限制；不能用“人口没满”证明有出生空间。

### 5.4 验收场景

| 场景 | 应看见什么 |
| --- | --- |
| 8 名同速短兵器近战冲向同一前排 | 队形停驻、合法前排接敌，后方不穿透挥砍 |
| 前排 + 3 名投掷/弓弩支援 | 前排承伤，射程内后排可同时输出 |
| 长矛在盾兵后方 | 是否输出由明确可达/越肩属性决定，画面能看懂 |
| 出口被堵后连续训练 | 项目完成后等待空间，无重叠刷兵 |
| 前排阵亡、受击退或同时阵亡 | 接战位置释放与补位稳定，两侧结果一致 |
| 大体型车/骑兵、英雄、召唤物混编 | 身体占位与特殊让行规则一致 |
| 单位 ID 改变，但布局/属性相同 | 不因编号余数改变排队结果 |
| 保存恢复、30/60/120 渲染帧率 | 同一输入的模拟结果一致，插值不改物理与伤害 |

这些才是后续需要补的规则测试。当前技术测试数量、图鉴包含全部角色、动作检视场景能打开，都不能作为这些条件已满足的证据。

占位和时代规则优先，因为它们决定动作该停在哪里、何时命中，以及 UI 应该显示哪些命令。UI 线框与资产标准可以准备，但不能在未定规则上批量做完所有动画。

技术路线继续使用现有 Phaser/TypeScript 与本地 Windows 工具，不需要换引擎、引入 3D、联网多人、Docker 或 WSL。五时代和既有内容可以复用；有问题的参数、角色职能、切片和效果要改，不能为了保住已有素材数量牺牲规则。
